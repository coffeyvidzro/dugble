<Warning>
    Outgoing webhooks are currently a preview. The catalog below is the
    complete set of events that endpoints can subscribe to during the preview.
</Warning>

Event types use a resource and lifecycle name, such as `email.delivered`,
`sms.delivered`, or `sms.failed`.

## Common envelope

The envelope includes a UUID event ID, an event type, the time the lifecycle
transition occurred, and a snapshot of the affected resource:

```json
{
    "id": "7fccf29e-d21e-4bc9-85a3-a4ec9c35a8dd",
    "type": "email.delivered",
    "occurred_at": "2026-07-31T12:01:10Z",
    "data": {
        "object": "email",
        "id": "49a3999c-0ce1-4ea6-ab68-afcd6dc2e794",
        "provider": "ses",
        "provider_message_id": "0100018f-example",
        "last_event": "delivery",
        "recipients": ["recipient@example.com"]
    }
}
```

Treat unknown fields and event types as forward-compatible additions. Do not fail an entire endpoint because it receives an event your application does not use.

## SMS events

| Event             | Meaning                                      | Suggested action                                            |
| ----------------- | -------------------------------------------- | ----------------------------------------------------------- |
| `sms.submitted`   | The provider accepted the SMS.               | Mark the message submitted.                                 |
| `sms.sent`        | The provider reported that the SMS was sent. | Continue waiting for final delivery when supported.         |
| `sms.delivered`   | The provider reported delivery.              | Mark the notification delivered.                            |
| `sms.undelivered` | The provider could not deliver the SMS.      | Verify the destination number before retrying.              |
| `sms.failed`      | Dugble could not complete delivery.          | Record the failure for operational review.                  |

## Email events

| Event                | Meaning                                             | Suggested action                                      |
| -------------------- | --------------------------------------------------- | ----------------------------------------------------- |
| `email.submitted`    | SES accepted the email for delivery.                | Mark the message submitted and await final outcomes.  |
| `email.delivered`    | SES delivered the email to the listed recipients.   | Mark those recipients delivered.                      |
| `email.delayed`      | SES reported a temporary delivery delay.            | Keep waiting or surface a delayed state.              |
| `email.bounced`      | SES reported a bounce for the listed recipients.    | Suppress permanent failures before retrying.          |
| `email.complained`   | A recipient reported the email as spam.             | Suppress the recipient and investigate the campaign.  |
| `email.rejected`     | SES rejected the email before delivery.             | Correct the message or sender configuration.          |
| `email.failed`       | SES could not render or otherwise send the email.   | Record the failure for operational review.            |

Email events include the affected recipient list from the provider event. A single
email can therefore produce different lifecycle events for different recipients.

## Test events

Sending a test from an endpoint creates a `webhook.test` event for that endpoint.
It uses the common envelope but is not a subscribable lifecycle event.

## Delivery headers and signature

Each request includes:

- `X-Dugble-Event`: event type
- `X-Dugble-Event-Id`: stable event UUID
- `X-Dugble-Delivery-Id`: UUID for this endpoint delivery
- `X-Dugble-Signature`: timestamped HMAC signature

The signature has the form `t=<unix_timestamp>,v1=<hex_digest>`. Compute the
expected digest with HMAC-SHA256, using the endpoint signing secret as the key
and `<unix_timestamp>.<raw_request_body>` as the signed bytes. Compare digests
with a constant-time function and reject timestamps outside your tolerance.

## Idempotent handling

Your endpoint should:

1. Verify the webhook signature against the raw request body.
2. Store the event ID with a unique constraint.
3. Acknowledge duplicate IDs without repeating side effects.
4. Queue application work and respond quickly.
5. Log unknown event types rather than returning an error.
